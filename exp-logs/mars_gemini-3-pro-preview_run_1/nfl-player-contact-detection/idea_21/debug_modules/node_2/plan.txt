The error analysis indicates that the `IndexError` is caused by negative values in the `step` column of the tracking data (e.g., `-185`), which correspond to frames before the play starts. The current implementation uses these `step` values directly as indices into a numpy array allocated based on `max_step`. Since numpy arrays do not support negative indexing in this context (and certainly not indices smaller than `-size`), this causes a crash. Furthermore, the downstream method `_compute_features_batch` assumes that index `0` of the tracking array corresponds to `step=0` (the snap).

To fix this, I will modify `_preprocess_tracking` in `library/feature_engineering.py` to explicitly filter out rows with negative steps before populating the lookup array. This resolves the crash by ensuring all indices are non-negative and valid, while maintaining the required alignment between array indices and time steps (Cite debug_lesson_25).
