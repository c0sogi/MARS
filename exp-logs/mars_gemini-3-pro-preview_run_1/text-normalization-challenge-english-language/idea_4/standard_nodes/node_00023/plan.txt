The issue is that the GPU memory from the first training stage (Tagger) is not being fully released before the second stage (Seq2Seq) begins, causing a `torch.OutOfMemoryError`. Despite explicit calls to garbage collection, internal references (likely from `DataLoader` or pinned memory) keep the tensors alive. To fix this, I will isolate each training stage in a separate Operating System process. This ensures that when the Tagger training process terminates, the OS forcibly reclaims all its resources, providing a clean slate for the Seq2Seq process (Cite debug_lesson_5). I will move the training logic into a new importable module `library/training_tasks.py` to satisfy `multiprocessing` requirements (Cite debug_lesson_6) and wrap the subprocess code in `try...except` blocks with `sys.stderr.flush()` to ensure any errors are properly reported (Cite debug_lesson_7, debug_lesson_8).
