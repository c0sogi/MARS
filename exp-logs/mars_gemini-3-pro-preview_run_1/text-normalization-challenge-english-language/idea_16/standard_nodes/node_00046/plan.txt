The root cause of the `torch.OutOfMemoryError` is the sequential execution of two memory-intensive training jobs (`TaggerTrainer` and `Seq2SeqTrainer`) within the same process. Even after the first model finishes, its resources (CUDA context, optimizer states, graph references) are not immediately or fully released by the Python garbage collector or the CUDA allocator. When the second model initializes, it attempts to allocate memory on top of the "zombie" footprint of the first model, exceeding the GPU capacity.

To fix this, I will isolate each training stage in a separate Operating System process using `multiprocessing`. This ensures that when a training stage completes, the OS forcibly reclaims all associated GPU resources, providing a clean slate for the next stage (Cite debug_lesson_5).

I will implement this by:
1.  Adding wrapper functions (`run_tagger_safe`, `run_seq2seq_safe`) to `library/trainer.py`. These functions will be importable by the child processes (Cite debug_lesson_6), accept configuration overrides to match the main script's settings, and wrap execution in a `try...except` block to ensure exceptions are printed and streams flushed (Cite debug_lesson_7, debug_lesson_8).
2.  Modifying `runfile.py` to use `torch.multiprocessing` to spawn these functions instead of calling the trainer classes directly.
