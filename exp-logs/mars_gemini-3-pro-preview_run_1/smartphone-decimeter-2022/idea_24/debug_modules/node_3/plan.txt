The issue is twofold:
1.  **Invalid WLS Baselines:** The raw GNSS logs contain epochs where the Weighted Least Squares (WLS) position is reported as `0.0` (Earth's center) instead of `NaN` when the chipset fails to calculate a fix. When these zero-coordinates are used as a baseline to compute ENU residuals against Ground Truth (in the US), the resulting distance is ~6,371 km. These outliers trigger the sanity filter (`< 1000 km`) in `_process_drive`, causing valid timestamped data to be discarded entirely.
2.  **Insufficient Data Selection:** The `runfile.py` demo script selects only a single drive for training. If that specific drive happens to have corrupted WLS data (all zeros or NaNs), the preprocessing pipeline yields an empty dataset, raising a `ValueError`.

To fix this:
1.  **Sanitize Inputs:** In `library/preprocessing.py`, explicitly replace `0.0` values in the WLS coordinate columns with `np.nan` *before* dropping missing values. This ensures invalid fixes are treated as missing data and removed upstream, preventing the generation of absurd target values.
2.  **Increase Robustness:** In `runfile.py`, modify the mini-dataset creation logic to select up to 3 drives instead of just 1. This increases the probability of including a drive with valid WLS data, ensuring the pipeline has data to process.

This applies **Lesson ID: debug_lesson_25** ("Avoid Indiscriminate Zero-Filling on Coordinate Reference Data") by actively identifying and removing invalid zero-coordinates used for spatial reference.
