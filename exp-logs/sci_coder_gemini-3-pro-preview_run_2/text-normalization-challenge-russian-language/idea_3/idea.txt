Based on the lessons learned, specifically the high baseline performance of the granular lookup hierarchy (Cite {solution_lesson_node_00006}) and its inability to handle the "infinite cardinality" of semiotic classes (Cite {solution_lesson_node_00002}), I propose a **Tiered Context-Aware Hybrid System**.

This approach fundamentally changes the architecture from a "Router" (which sends *all* numbers to a model) to a "Cascade" (which prioritizes memory and only uses the model for *unseen* complex cases).

# Model

The solution consists of two distinct inference engines arranged in a prioritized cascade:

1.  **Tier 1: Granular HFBB (The Memory Engine)**
    *   This component acts as a high-precision cache. It utilizes the optimized 5-level backoff hierarchy: **Trigram $\rightarrow$ Bigram (Prev) $\rightarrow$ Bigram (Next)**.
    *   **Role:** It resolves all "seen" context-dependent normalizations instantly. For example, if "Chapter 5" appears in the training set, the Bigram `(Chapter, 5)` will be stored, and this tier will handle it correctly without needing neural inference.
    *   **Retention:** This explicitly preserves the successful granular backoff strategy (Cite {solution_lesson_node_00006}).

2.  **Tier 2: Character-Level Contextual Transformer (The Generative Engine)**
    *   **Architecture:** A lightweight Transformer-based Encoder-Decoder (e.g., based on BART or T5 architecture configs) trained from scratch.
    *   **Input:** A character-sequence representation of the target token flanked by its neighbor words to capture morphological context (e.g., case agreement).
        *   Format: `<prev_word> <SEP> <target_token> <SEP> <next_word>`
    *   **Output:** The normalized character sequence.
    *   **Role:** This engine is invoked *only* when the Memory Engine fails to find a match in the high-order contexts (Trigram/Bigram) *and* the token is identified as "semiotic" (contains digits). This addresses the "tail" of the distribution (Cite {solution_lesson_node_00002}).

3.  **Inference Logic (The Cascade):**
    *   **Step 1:** Query Tier 1 (Trigram $\rightarrow$ Bigram_Prev $\rightarrow$ Bigram_Next). If a match is found, return it immediately. This ensures we prioritize "known facts" over "predictions".
    *   **Step 2:** If Tier 1 misses, check if the token contains digits (Semiotic Filter).
        *   **If Semiotic:** Dispatch to **Tier 2** (Transformer). This handles unseen numbers (e.g., "$9,421.55") that lookup tables cannot resolve.
        *   **If Non-Semiotic:** Fall back to HFBB Unigram $\rightarrow$ Identity.

# Data

1.  **HFBB Preparation:**
    *   Process the full training corpus to build the Trigram, Bigram (Prev), Bigram (Next), and Unigram frequency maps.
    *   Apply the "Group Shuffle Split" strategy to ensure validation integrity.

2.  **Transformer Preparation:**
    *   **Filtering:** Create a training subset containing *only* tokens where the `before` text contains a digit (`\d`). This reduces the training set size by ~90%, allowing for rapid convergence on the specific problem domain (semiotic normalization).
    *   **Tokenization:** Use a **Character-Level Tokenizer**. As noted in the lessons, subword tokenization is suboptimal for number expansion. A custom character vocabulary (built from the filtered subset) ensures the model learns the precise mapping of digits to letters.
    *   **Context Windowing:** For each sample, extract the preceding and succeeding words from the `sentence_id` group. If at a sentence boundary, use `<BOS>`/`<EOS>` tokens.

# Training

1.  **HFBB:**
    *   Constructed via single-pass Maximum Likelihood Estimation (counting frequencies and selecting the mode).

2.  **Transformer:**
    *   **Objective:** Minimize Cross-Entropy Loss on the target character sequence.
    *   **Optimization:** Use AdamW optimizer with a "OneCycle" or linear warmup learning rate scheduler to stabilize training on the character-level objective.
    *   **Regularization:** Apply dropout (0.1) and label smoothing (0.1) to prevent overfitting on the specific numbers seen in the training subset.

# Evaluation

1.  **Inference Pipeline:**
    *   Load the HFBB Hash Maps and the trained Transformer checkpoint.
    *   Iterate through the test set tokens.
    *   Apply the **Cascade Logic**:
        *   Check Trigram/Bigrams. If hit $\rightarrow$ Predict.
        *   Else if `has_digit(token)` $\rightarrow$ Run Transformer Inference (Greedy or Beam Search width=3).
        *   Else $\rightarrow$ Check Unigram $\rightarrow$ Identity.
2.  **Submission:**
    *   Reconstruct the predictions into the `id,after` CSV format.

This strategy optimally balances the high precision/speed of the HFBB baseline (Cite {solution_lesson_node_00006}) with the generalization capabilities of a neural network, strictly confined to the problem areas identified in the failure analysis (Cite {solution_lesson_node_00002}).
