# Idea 6: Fine-Grained Transformation Classification via Inverse Label Engineering

This strategy proposes a structural evolution of **Idea 5 (Transformer-CRF)**. While Idea 5 correctly identifies the semiotic class (e.g., `DATE`), it fails to address **intra-class ambiguity** where the formatting logic depends on context (e.g., the token "12" in a `DATE` context could be normalized as "twelve" or "twelfth"). This proposal shifts the problem formulation from **Entity Recognition** (predicting *what* something is) to **Transformation Prediction** (predicting *how* to process it), ensuring the downstream rule execution is fully deterministic.

### Model
**Architecture**: The backbone is a pre-trained Transformer Encoder (e.g., `roberta-base`) which provides deep, bidirectional contextual embeddings.
*   **Structural Innovation**: Instead of predicting the 15 raw classes provided in the dataset (which are semantic categories), the classification head predicts a set of **Fine-Grained Transformation IDs** (derived during data preprocessing).
*   **Reasoning**: A standard `DATE` label is insufficient for a deterministic rule engine because it does not specify whether to read a number as a cardinal, ordinal, or year. By predicting a precise label like `DATE_ORDINAL` or `DATE_YEAR`, we leverage the Transformer's attention mechanism to resolve the ambiguity, allowing us to "decouple classification from generation" and "delegate text generation to deterministic code" without requiring the code to handle complex context logic Cite {solution_lesson_node_00006}.

### Data
**Preprocessing (Inverse Label Engineering)**:
1.  **Label Derivation**: We iterate through the training set to "reverse engineer" the specific transformation logic used for each token. By comparing the `before` (raw) and `after` (normalized) text within each class, we subdivide the original classes into granular **Transformation IDs**.
    *   *Example*: If `class` is `DATE`:
        *   "12" $\to$ "twelve" $\implies$ Label: `DATE_CARDINAL`
        *   "12" $\to$ "twelfth" $\implies$ Label: `DATE_ORDINAL`
        *   "1998" $\to$ "nineteen ninety-eight" $\implies$ Label: `DATE_YEAR`
    *   This process expands the label space from ~15 to ~50-100 specific actions.
2.  **Strategic Sampling**: We retain the "Hard-Negative" strategy from Idea 5. We keep 100% of sentences containing non-`PLAIN` tokens. For the majority `PLAIN` class, we filter sentences using regex heuristics (e.g., keeping plain sentences with digits or capitalization) to provide the model with difficult "distractor" examples, while discarding trivial lowercase text to improve training efficiency.

### Training
**Procedure**:
*   **Objective**: The model is trained as a Token Classifier using Cross-Entropy Loss over the new **Fine-Grained Transformation ID** space.
*   **Optimization**: We use the AdamW optimizer with a linear learning rate scheduler.
*   **Advantage**: By baking the formatting decision into the label (e.g., `DATE_ORDINAL`), the model learns to associate specific contexts (like the word "January" preceding a number) directly with the required formatting action, removing the need for a complex, context-aware rule engine.

### Evaluation
**Inference**:
1.  **Predict**: The test sentences are fed into the Transformer, which outputs the most likely **Transformation ID** for each token.
2.  **Execute**: We maintain a registry mapping each Transformation ID to a specific, simple Python function (e.g., `ID_DATE_ORDINAL` maps to a function that converts digits to ordinal words).
3.  **Generate**: The raw token is passed to the selected function to generate the final string. This ensures 100% adherence to the "deterministic code" principle Cite {solution_lesson_node_00006}, as the code performs a single, unambiguous operation.
