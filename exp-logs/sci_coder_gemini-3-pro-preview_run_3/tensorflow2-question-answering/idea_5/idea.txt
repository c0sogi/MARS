### Model
The proposed solution is a **Feature-Based Boosting Ranker and Recurrent Reader**. This approach diverges from the previous embedding-based neural rankers by utilizing classical Information Retrieval (IR) features with a tree-based model for ranking, followed by a lightweight recurrent network for extraction.

1.  **Long Answer Ranker (Gradient Boosting Machine):**
    *   **Architecture:** A **Gradient Boosting Decision Tree (GBDT)** (e.g., LightGBM) is used instead of a neural network. It operates on a vector of engineered scalar features rather than raw text embeddings.
    *   **Input:** A feature vector representing the relationship between the Question and a Candidate Long Answer (paragraph).
    *   **Function:** The tree ensemble learns non-linear interactions between lexical and structural signals to output a probability score indicating whether the candidate contains the answer.

2.  **Short Answer Reader (Stacked Bi-GRU):**
    *   **Architecture:** A **Stacked Bi-Directional Gated Recurrent Unit (GRU)** network. GRUs are selected over LSTMs for their computational efficiency (fewer gates and parameters).
    *   **Input:** A sequence of word embeddings representing the Question concatenated with the Top-Ranked Candidate Paragraph.
    *   **Output:** The hidden states from the GRU layers are passed to two independent dense layers that predict the logits for the `start` and `end` token indices of the short answer span.

### Data
*   **Preprocessing:**
    *   **Segmentation:** The raw `document_text` is parsed to extract candidate blocks based on top-level HTML tags (e.g., `<P>`, `<Table>`, `<Ul>`).
    *   **Feature Engineering (Ranker):** For every Question-Candidate pair, a set of features is computed:
        *   **Lexical:** BM25 score, TF-IDF cosine similarity, and raw unigram/bigram overlap counts.
        *   **Structural:** Boolean flags indicating the tag type (e.g., `is_table`), the length of the paragraph, and its relative position index within the document.
    *   **Tokenization (Reader):** Text is tokenized by splitting on whitespace and mapped to indices based on pre-trained static embeddings (e.g., GloVe).
*   **Dataset Construction:**
    *   **Ranker Data:** A tabular dataset is created. Positive rows correspond to ground-truth paragraphs. Negative rows are generated using **BM25 Hard Negatives** (top-k retrieved paragraphs that do not contain the answer) to force the tree model to learn features beyond simple keyword matching.
    *   **Reader Data:** Only positive paragraphs containing valid short answers are used. Start and end indices are adjusted to be relative to the start of the paragraph.

### Training
*   **Strategy:** The Ranker and Reader are trained as completely independent systems.
*   **Ranker Optimization:** The GBDT is trained using **Binary Log Loss** (or a ranking objective like LambdaRank) to minimize classification error on the tabular data. This process is CPU-efficient and does not require GPU resources.
*   **Reader Optimization:** The Bi-GRU is trained using **Categorical Cross-Entropy Loss** for the start and end positions. The Adam optimizer is used with gradient clipping to ensure stability.

### Evaluation
1.  **Candidate Generation:** The test document is segmented into candidate paragraphs.
2.  **Feature Extraction:** The defined lexical and structural features are computed for every Question-Candidate pair in the document.
3.  **Ranking:** The GBDT Ranker predicts a relevance score for each candidate. The candidate with the highest score is selected as the Long Answer.
4.  **Extraction:** The text of the selected candidate is tokenized and passed (along with the question) to the Bi-GRU Reader, which outputs probability distributions for the start and end tokens.
5.  **Inference:** The valid span (`start <= end`) with the highest joint probability is identified. If the Ranker's score is below a tuned threshold, the system predicts "Null"; otherwise, it returns the predicted Long Answer indices and Short Answer text.
