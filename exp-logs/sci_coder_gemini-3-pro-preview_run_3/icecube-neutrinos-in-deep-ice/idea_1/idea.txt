To establish a robust, efficient, and distinct baseline, I propose a **Shared-Weight Pulse Encoder (PointNet-style) Architecture**. This approach treats the neutrino event as an unordered set of pulses (a point cloud) rather than a sequence or a graph. It is computationally cheaper than GNNs or Transformers because it processes pulses independently before aggregation, avoiding the quadratic complexity of attention or the neighbor-search overhead of graph construction.

### Model
The architecture consists of three lightweight stages:
1.  **Pulse-wise Feature Extraction:** The input is a tensor of shape $(B, N, F)$, where $B$ is the batch size, $N$ is a fixed number of sampled pulses, and $F$ represents the features (spatial coordinates $x, y, z$, relative time, charge, and auxiliary status). A Multi-Layer Perceptron (MLP) is applied to each pulse **independently**. Crucially, the weights of this MLP are shared across all pulses. This stage maps the raw low-level features of a single pulse to a higher-dimensional latent embedding.
2.  **Symmetric Aggregation:** To generate a representation of the entire event that is invariant to the order of the pulses, a **Global Max Pooling** operation is applied across the $N$ pulse embeddings. This extracts the most salient features (e.g., the earliest time, the highest charge concentration) from the set into a single global feature vector.
3.  **Direction Regression Head:** The global feature vector is passed through a final MLP to predict the 3D direction vector $(n_x, n_y, n_z)$ of the neutrino. Predicting the vector components is numerically more stable than predicting angles directly due to the periodicity of azimuth.

### Data
1.  **Geometry Merging:** Map the `sensor_id` in the batch files to the physical $(x, y, z)$ coordinates using `sensor_geometry.csv`.
2.  **Normalization:** Normalize the `time` feature relative to the start of the event (or the first pulse). Log-transform the `charge` feature to handle its wide dynamic range. Scale spatial coordinates to a standard range (e.g., divide by detector bounds).
3.  **Sampling & Padding:** To enable efficient batch training on the GPU, inputs must have a fixed size. For each event, select the top $N$ pulses (e.g., $N=128$) with the highest `charge`. If an event has fewer than $N$ pulses, pad the remaining slots with zeros (and use masking if necessary, though Max Pooling handles zero-padding naturally if using ReLU activations).

### Training
-   **Loss Function:** Use **Cosine Similarity Loss** (or $1 - \text{cosine\_similarity}$). This explicitly minimizes the angular error between the predicted vector and the ground truth vector derived from the target azimuth and zenith. This is directly aligned with the competition metric (Mean Angular Error).
-   **Optimizer:** Use the **Adam** optimizer with a standard learning rate (e.g., 1e-3) and a learning rate scheduler (e.g., ReduceLROnPlateau) to refine convergence.
-   **Strategy:** Train for a fixed number of epochs or until validation loss plateaus. Given the "baseline" philosophy, avoid heavy regularization techniques like Mixup or complex augmentation.

### Evaluation
1.  **Inference:** Iterate through the test set batches. Apply the same preprocessing (geometry merging, normalization, top-charge sampling) used in training.
2.  **Post-processing:** The model outputs a 3D vector $(n_x, n_y, n_z)$. Normalize this vector to unit length.
3.  **Coordinate Conversion:** Convert the normalized unit vector back to spherical coordinates:
    -   `zenith` = $\arccos(n_z)$
    -   `azimuth` = $\arctan2(n_y, n_x)$ (ensure the result is mapped to $[0, 2\pi]$).
4.  **Submission:** Format the resulting event IDs and angles into the required CSV format.
