Based on the task requirements and the provided dataset analysis, I propose a highly efficient baseline solution that prioritizes speed and simplicity while effectively addressing the repetitive nature of the text normalization task.

### Model
**Architecture: Hierarchical Symbolic Retrieval with Regex Fallback**

This approach treats text normalization primarily as a memory retrieval task rather than a generative or classification one. It relies on the observation that the vast majority of tokens (93%+) are identity mappings, and of those that change, most follow a deterministic pattern based on their string value and immediate context. The model consists of a three-tiered hierarchy:

1.  **Contextual Bigram Memory (L2 Cache)**: A hash map where keys are `(previous_token, current_token)` tuples and values are the most frequent normalized strings observed in the training data. This layer resolves context-dependent ambiguities (e.g., distinguishing "St." as "Street" vs. "Saint" based on the preceding word).
2.  **Unigram Memory (L1 Cache)**: A hash map keyed by the `current_token` string alone, mapping to its global mode (most frequent) normalization. This handles high-frequency, context-independent normalizations (e.g., "$" $\rightarrow$ "dollars", "Jan" $\rightarrow$ "January").
3.  **Heuristic Regex Transducer (Fallback)**: A lightweight, rule-based module for Out-of-Vocabulary (OOV) tokens. It utilizes Regular Expressions to detect numerical patterns (integers, decimals, years) in unseen tokens and applies a deterministic algorithmic conversion (e.g., a custom digit-to-text function). If no pattern matches, it defaults to the identity mapping (returning the raw token).

### Data
**Preprocessing for Training**:
The training data (`train.parquet`) will be processed in a single sequential pass. We will iterate through the dataset to extract:
1.  **Unigram Counts**: Frequency of each `(before_token) -> after_token` mapping.
2.  **Bigram Counts**: Frequency of each `(previous_token, before_token) -> after_token` mapping.

**Preprocessing for Evaluation**:
The test data (`test.parquet`) requires minimal preprocessing. We simply need to load the tokens and shift the sequence to generate the `previous_token` feature for the bigram lookup.

### Training
**Procedure**:
This approach utilizes a "lazy learning" or "count-based" training strategy, which eliminates the need for gradient descent or iterative optimization.
1.  **Aggregation**: Aggregate the counts collected during data preprocessing.
2.  **Selection**: For every unique unigram and bigram key, select the target string with the highest frequency (Maximum Likelihood Estimation).
3.  **Pruning**: To maintain efficiency and reduce noise, bigram entries with very low frequency (e.g., appearing only once) can be discarded, allowing the model to fall back to the robust unigram statistics.

This training phase is extremely fast, likely completing in minutes even on the full dataset.

### Evaluation
**Prediction Process**:
For each token in the test set, the model follows a strict cascade:
1.  **Query L2 (Bigram)**: Check if the `(previous_token, current_token)` pair exists in the Bigram Memory. If a hit is found, output the stored value.
2.  **Query L1 (Unigram)**: If L2 misses, check if the `current_token` exists in the Unigram Memory. If a hit is found, output the stored value.
3.  **Apply Fallback**: If L1 misses, pass the token to the Heuristic Regex Transducer. If it matches a known numerical pattern, generate the text; otherwise, predict the original token string.

This pipeline ensures that common cases are handled instantly via lookup, while rare numerical entities are handled algorithmically, providing a strong and computationally efficient baseline.
