The training failure (`Train Loss: nan`) is caused by numerical overflow when converting raw GNSS features from `float64` to `float32`. Specifically, some uncertainty fields in the dataset likely contain sentinel values (e.g., `1e100` or larger) representing unknown/invalid measurements. While valid in `float64`, these exceed the maximum value of `float32` (~3.4e38) and become `Infinity`. When these infinities are passed to the `BatchNorm1d` layer (the first layer of the model), the mean and variance calculations result in `NaN`, which propagates through the network.

To fix this, I will:
1.  **Sanitize Data in `library/data.py`**: Implement a `_clean_features` function that replaces `Infinity` with `NaN`, fills `NaN`s with 0, and clips all values to a safe range (e.g., `[-1e9, 1e9]`) before the data is converted to tensors. This applies the guidance from **Cite debug_lesson_1**.
2.  **Clear Cache in `runfile.py`**: Add a step to clear the cached parquet files at the beginning of execution to ensure the data is re-processed with the new cleaning logic.
